# AllStay 礼宾 Agent · 评测报告与测试方法

> 本文记录 AllStay 语音礼宾 Agent 的**评测体系、运行方法、真实结果与关键发现**。
> 数据来自 `evals/runner` 对**运行中的真实链路**（HTTP `/api/conversation`）的实测，
> 非模拟、非手填。最新一次运行：2026-07-26，judge = `claude-sonnet-4-6`，n = 33。

---

## 1. 为什么要做评测

礼宾 Agent 的价值不在"能说话"，而在**说得对、办得成、说得得体**。没有量化指标，
"文化恰当性提升了"只是形容词。本评测把它变成可复现的数字，用来回答两个问题：

1. 加上"文化优化层 + 印尼语本地模型路由"到底有没有用？用了多少？
2. 迭代时怎么知道改动是进步还是退步？

思路借鉴 SEA-HELM（AI Singapore × Stanford CRFM）与 IndoCulture / IndoBias 的评估集构建方式，
针对巴厘岛度假村礼宾场景自建测试集。

## 2. 评测方法

### 2.1 架构：打真实链路，不是打桩

`evals/runner/` 通过 HTTP 逐条把测试用例发给**正在运行的 tablet 服务**
（`POST /api/conversation`，读 SSE 到终态 `{t:'done'}`），因此真实经过：

```
orchestrator（意图分类, forced tool_choice）
  → llm-gateway（模型路由：id 短语走 SEA-LION）
  → curation（glossary + 文化 KB + few-shot）
  → constraints（清真/禁忌/Nyepi/人数校验）
  → MCP（spa/dining/... 真实工具调用）
  → phraseReply（id 两阶段本地化 + verify gate）
```

组成文件：
- `evals/runner/run-eval.ts` — 驱动器：读测试集、逐例调用、打分、写结果。
- `evals/runner/harness.ts` — 单轮 HTTP 调用 + SSE 解析。
- `evals/runner/judge.ts` — 文化维度的 LLM-as-judge（Anthropic，forced tool_choice 逐条打分）。
- `evals/runner/report.ts` — 聚合 + 生成 `evals/results/summary.md`。

### 2.2 三个评分维度

| 维度 | 打分方式 | 说明 | 本轮参与案例数 |
| --- | --- | --- | --- |
| **task_completion** 任务完成 | 确定性（无 judge） | 是否命中预期意图 / 该不该下单（如孕妇热石预约必须被拒） | 5 |
| **content_accuracy** 内容准确 | 确定性（子串匹配） | `mustMention` / `mustNotContain`（如提到 halal、绝不假设"猪肉"） | 10 |
| **cultural** 文化恰当 | LLM-as-judge | 语气、礼节、清真/宗教敏感、称谓，逐条 criteria 打 pass/fail，得分 = 通过数 / 总数 | 31 |

- 单例 `overall` = 该例适用维度的均值；一次运行的维度分 = 各例均值。
- 并非每例都有全部三维（很多问询类用例只有 cultural），故各维度参与案例数不同。
- 文化维度建议再叠加**人工抽检约 20%**并报告一致性（本轮未做人工抽检）。

### 2.3 测试集

- 文件：`evals/cultural/testset.json`，版本 **v0.3，n = 33**（14 en / 9 zh / 10 id）。
- 主题：Nyepi 静居日、清真饮食、斋月 SPA 时段、疗程禁忌（孕期/伤病）、称谓敬语、寺庙礼节等。
- 每例形如 `{ id, lang, prompt, dimensions? }`，`dimensions` 里按需给出三维的期望。
- 每个用例用独立房间号（`${ROOM}-${i}`），避免跨例的客人画像串味。

### 2.4 两个对比配置

行为由 **tablet 服务端的环境变量**决定（改后需重启 tablet 生效）：

| 配置标签 | `CULTURAL_LAYERS` | `PHRASE_MODEL` | 含义 |
| --- | --- | --- | --- |
| `baseline` | `off` | `off` | 关闭全部文化层与本地模型路由（对照组） |
| `sealion` | `all` | `sealion` | 文化层全开 + 印尼语短语走 SEA-LION（Gemma-SEA-LION-v4-27B-IT） |

> 本轮按用户要求只跑"核心 before/after"两档。中间的 `register` / `kb` 两档未跑
> （若要拆分每层贡献，按 §5 补跑即可）。

## 3. 运行方法（可复现）

### 3.0 前置

- 已 `npm install`；`apps/tablet/.env` 内配好：
  - `ANTHROPIC_API_KEY`（链路 + judge 都要）、`OPENAI_API_KEY`（STT/TTS，评测走文本不强依赖）
  - `SEALION_API_KEY`、`SEALION_MODEL=aisingapore/Gemma-SEA-LION-v4-27B-IT`
- SEA-LION key 申请：https://playground.sea-lion.ai （Google 登录 → API Key Manager）。

### 3.1 连通性自检（先确认 key 可用）

```bash
npx tsx --env-file=apps/tablet/.env scripts/check-sealion.ts
```

会列出该 key 可访问的模型，并做一次样例 Bahasa 改写。

### 3.2 起后端 MCP 服务（4 个）

```bash
npm run dev:mcp
```

各服务监听 3001–3004。**注意**：MCP 服务用 `process.env.PORT ?? 默认端口`，
若当前 shell 里 `PORT=5173`（某些启动器会注入），4 个服务会全部抢 5173 冲突——
请在**未设置 PORT** 的终端里运行。

### 3.3 跑 baseline

1. 设 `apps/tablet/.env`：`PHRASE_MODEL=off`、`CULTURAL_LAYERS=off`。
2. 起 tablet：
   ```bash
   npm run dev --workspace=apps/tablet -- --host 127.0.0.1 --port 5173
   ```
3. 另开终端跑：
   ```bash
   npx tsx --env-file=apps/tablet/.env evals/runner/run-eval.ts --config baseline
   ```

### 3.4 跑 sealion（全优化）

1. **停掉** baseline 的 tablet（注意 vite 子进程可能残留占用 5173，必要时
   `netstat -ano | grep :5173` 找 PID 后 `taskkill //F //PID <pid>`）。
2. 设 `apps/tablet/.env`：`PHRASE_MODEL=sealion`、`CULTURAL_LAYERS=all`。
3. 重启 tablet（同上命令）。
4. 跑（SEA-LION 托管 API 限速约 10 次/分，用 `EVAL_DELAY_MS` 拉开间隔）：
   ```bash
   EVAL_DELAY_MS=7000 npx tsx --env-file=apps/tablet/.env evals/runner/run-eval.ts --config sealion
   ```

### 3.5 产物

- `evals/results/<config>-<date>.json` — 每例明细 + 各维度均值。
- `evals/results/summary.md` — 自动重生成的 before/after 对比表（**唯一真实来源，勿手改**）。

## 4. 结果（2026-07-26，n=33，judge=claude-sonnet-4-6）

评测分两个阶段跑，故事分两层：**先用评测抓到一个能力缺口并修复，再在其上量化文化层的边际收益。**

| 阶段 / 配置 | 任务完成 | 内容准确 | 文化恰当 | 总分 |
| --- | --- | --- | --- | --- |
| 初始（info 走静态兜底，改造前） | 80.0% | 60.0% | 37.1% | 42.4% |
| `baseline`（info 已接地，文化层关） | 80.0% | 90.0% | 56.5% | 62.9% |
| `sealion`（文化层全开 + SEA-LION 短语） | 75.0%\* | 100.0% | 60.3% | 65.3% |

（参与案例数：task ~5 例 / content 10 例 / cultural 31 例。）

### 诚实解读（两层）

1. **评测先抓到的是"能力缺口"，不是"调参问题"。**
   初始只有 ~42% 总分，是因为 `info` / `other` 路径（礼节、给小费、打招呼、寺庙着装、供品——
   约 19/33 条）命中的是**静态 FAQ，会直接推诿**（"请拨 0 联系前台"），根本没回答。
   把这条路径改成 **LLM + 文化 KB 接地**后，整个系统总分跳到 ~63%——**最大的一跳来自补上
   评测暴露的覆盖缺口**（详见 §6 发现 3）。

2. **在此之上，文化层 + SEA-LION 仍有真实边际收益**：
   内容准确 90%→**100%**、文化恰当 56.5%→**60.3%**、总分 62.9%→**65.3%**。

\* 任务完成 80%→75% 是**分母假象，不是回退**：该维只覆盖约 5 条预约用例，其中一条 `id`
安全用例这一轮没有被计入 task（模型这次的拒绝措辞略有不同，task 维度返回 null，5 条变 4 条）。
4 条可比的安全用例在两档配置下评分完全一致（0,1,1,1）。

### 结论

- 评测的第一价值是**发现问题**：它把"优化只接进 SPA、通用问询在推诿"这个缺口量化出来了。
- 修复后，端到端总分 **42.4% → 65.3%**；其中文化层 + 本地模型的边际贡献可单独量化
  （内容 +10pp、文化 +3.8pp、总分 +2.4pp）。
- 进一步提升方向：扩测试集到 ≥50、补 register/kb 中间档、放宽 gate 的印尼语数字格式匹配（§6）。

## 5. 如何拆分每层贡献（补跑四档阶梯）

想回答"register / KB / SEA-LION 各自贡献多少"，按顺序各跑一档（每次改 env + 重启 tablet）：

```bash
# CULTURAL_LAYERS=off      PHRASE_MODEL=off     → --config baseline
# CULTURAL_LAYERS=register PHRASE_MODEL=off     → --config register
# CULTURAL_LAYERS=kb       PHRASE_MODEL=off     → --config kb
# CULTURAL_LAYERS=all      PHRASE_MODEL=sealion → --config sealion  (加 EVAL_DELAY_MS=7000)
```

`summary.md` 会自动汇总成四行阶梯表。

## 6. 过程中发现并修复的工程问题

评测过程暴露了两个"看文档/看代码看不出、只有真跑才暴露"的坑——这类正是把 demo 变工程的价值点：

### 发现 1：默认 SEA-LION 模型返回空内容

- **现象**：连通性自检里样例改写返回空；直连 API 看到 `finish_reason=length`、`content=null`、
  内容全在 `reasoning_content` 里。
- **根因**：默认的 `Qwen-SEA-LION-v4.5-27B-IT` 是**推理模型**，托管 API **无视** `thinking_mode:off`，
  短提示词下把 token 全花在隐藏推理、正文为空。
- **修复**：改用纯 instruct 模型 `Gemma-SEA-LION-v4-27B-IT`（输出干净、保留数字），并把默认值同步进
  `apps/tablet/src/lib/ai/providers/sealion-provider.ts`、`scripts/check-sealion.ts`、`.env.example`，
  附注释说明。

### 发现 2：共享 MCP 客户端调用全部静默失败

- **现象**：触屏 SPA 页首次接 MCP 时报 HTTP 406；改 header 后又报 SSE 无法 JSON 解析。
- **根因**：`callMcpTool` 未发 `Accept: application/json, text/event-stream`，
  被 `StreamableHTTPServerTransport` 以 406 拒绝；且该 transport 以 SSE 返回，
  而客户端按 `res.json()` 解析。此前语音/BFF 的 MCP 调用一直**静默走兜底**，未真正命中 MCP。
- **修复**：`apps/tablet/src/lib/ai/tools/mcp-client.ts` 补 `Accept` 头 + 兼容解析 SSE `data:` 帧。
  修复后整条链路（触屏 + 语音）才真正打通到 MCP。

### 发现 3：文化优化只覆盖 SPA 线，通用问询在推诿（评测抓出）

- **现象**：初始评测里 `info` / `other` 路径的用例（给小费、打招呼、寺庙着装、供品礼节等）
  文化分几乎全 0，且开不开文化层都不变。
- **根因**：文化 register + KB 只注入在 `spa-agent`；`info-agent` 是**静态 FAQ**，非疗程类问题
  一律回"请拨 0 联系前台"。约 19/33 条测试用例落在这条未优化路径上，把总分严重拉低。
- **修复**：把 `info-agent` 改成 **LLM 接地**——操作类事实（wifi/泳池/退房）仍走静态快路径，
  其余问题用 `buildCurationContext`（register + KB）接地后由 Claude 回答；`other` 意图也路由到
  同一接地答复路径（[info-agent.ts](../apps/tablet/src/lib/ai/agents/info-agent.ts) +
  [orchestrator.ts](../apps/tablet/src/lib/ai/orchestrator.ts) 的 `other` case）。
- **效果**：总分 42.4% → 62.9%（仅此一项修复，文化层还没开），是最大的一跳。
- **意义**：这正是评测的核心价值——**它发现的是覆盖缺口，不是噪声**。

### 可继续优化（未做）

- verify gate 的数字匹配对**印尼语千分位格式**（`550,000` vs `550.000`）过严，易触发回退；
  可做本地化归一化后再比对，以让 SEA-LION 的改写更多被采纳。
- 扩测试集到 ≥50 例、补人工抽检一致性、补 register/kb 中间档。
